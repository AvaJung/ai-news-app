뉴스 수집기 앱의 새 기능 개발 워크플로우를 아래 순서대로 진행해. 브랜치 이름: $ARGUMENTS

## 1. 현재 상태 확인

- `git status`와 `git branch --show-current`로 현재 상태를 확인해.
- 현재 브랜치가 main이 아니면 경고를 보여주고, main으로 이동할지 사용자에게 물어봐. 답을 받기 전에는 이동하지 마.
- 커밋하지 않은 변경이 있으면 목록을 보여주고 어떻게 할지 물어봐.

## 2. 새 브랜치 만들기

- `$ARGUMENTS`가 비어 있으면 어떤 기능을 개발할 것인지 물어봐. 답을 듣고 영어 소문자-하이픈 형식(예: `add-category-crud`)으로 브랜치 이름을 제안하고, 사용자가 확인하면 사용해.
- `git branch --list <이름>`으로 같은 이름의 브랜치가 이미 있는지 확인해. 있으면 만들지 말고 알려준 뒤 다른 이름을 물어봐.
- 이름이 정해지면 `git checkout -b <이름>`으로 브랜치를 만들어.

## 3. 개발 시작 안내

- 브랜치 생성이 끝나면 "이제 개발을 시작하세요!"라고 안내해.
- `CLAUDE.md`를 읽고 이 프로젝트의 기술 스택과 컨벤션을 다시 알려줘. 최소한 다음을 짧게 정리해.
  - 기술 스택, 구현된 범위와 아직 없는 것
  - Next.js 16 특이사항 (`src/proxy.ts`, `cacheComponents` 등)
  - 아키텍처 규칙 (진입점마다 Clerk 로그인과 `ALLOWED_EMAILS` 확인, 오케스트레이션은 의존성 주입)
  - 구현 전에 `PRD.md`를 읽고, 화면 작업은 `ui.md`를 따른다는 점
- 이후 사용자가 개발을 요청하면 평소처럼 도와줘.

## 4. 완료 처리

사용자가 "완료" 또는 "done"이라고 입력하면:

1. `git status`와 `git diff --stat`으로 변경된 파일 목록을 보여줘.
2. 변경 내용을 바탕으로 커밋 메시지를 제안해. 이 저장소의 기존 커밋처럼 한국어로 한 줄로 쓰고, `git log --oneline -5`로 스타일을 확인해.
3. 사용자가 확인하면 변경 파일을 add하고 커밋해. 사용자가 메시지를 고치면 그대로 따라.
4. 커밋 후 `git checkout main`으로 이동해서 `git merge <브랜치 이름>`으로 병합해. 충돌이 나면 병합을 멈추고 충돌 파일을 보여준 뒤 어떻게 할지 물어봐.
5. `.env*` 같은 비밀 파일이 커밋 대상에 섞여 있으면 커밋하지 말고 알려줘.

## 5. 마무리 요약

병합이 끝나면 다음을 요약해서 보여줘.

- 브랜치 이름과 병합 결과
- 커밋 메시지와 변경된 파일 목록
- 이번에 개발한 내용 한두 문장
- 병합된 브랜치를 지울지 물어봐. 사용자가 원할 때만 `git branch -d`로 지워.
